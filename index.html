Overview

여러 판매자가 한 플랫폼에 입점하는 멀티 셀러 오픈마켓입니다. 판매자가 등록한 상품은 관리자가 승인해야 게시되고, 한 주문에 여러 판매자 상품이 섞이므로 배송과 정산을 판매자별로 분리해야 합니다. 상품 등록 → 관리자 승인 = 게시 → 주문 → 결제 → 판매자별 배송 → 구매 확정 → 정산까지 이커머스 전체 흐름을 1인 풀스택으로 구현했고, 배포 후 실제로 운영하면서 관리자 AI 어시스턴트(사내 데이터 LLM), Sentry 관측, nginx/HTTPS, 접근성 개선을 더했습니다. 본 포트폴리오는 프론트엔드 직무 기준으로 서술하며, 백엔드·인프라는 보조로 둡니다.

시스템 구조 — 브라우저는 같은 출처로, 앱과 웹훅은 직접

브라우저가 EC2를 직접 부르면 도메인이 달라 refresh 쿠키가 어긋납니다. 그래서 브라우저는 Vercel rewrites로 /api/*를 같은 출처처럼 부르고, 로그인·갱신·로그아웃은 Next.js BFF가 쿠키를 처리합니다. API는 EC2의 nginx(TLS 종료·Let's Encrypt) 뒤에서 NestJS로 운영하며, nginx/HTTPS를 도입할 때도 브라우저 경로는 그대로 두었습니다. PortOne 결제 웹훅(웹훅 경로만 IP 허용)과 React Native 운영 앱(쿠키 없이 토큰)은 nginx로 직접 들어옵니다. 이 구조 때문에 브라우저 경로가 한 홉 더 길어 결제 확정에서 경합이 기본값이 되었고, 이를 트러블슈팅 ③에서 다룹니다. 인증은 Access=메모리 / Refresh=httpOnly 쿠키 회전, 데이터는 RSC에서 prefetch → dehydrate → HydrationBoundary로 넘긴 뒤 TanStack Query가 캐시·무효화를 담당합니다.

JWT 인증 + 멀티탭 동기화
새 탭에서도 로그인 유지, 로그아웃은 모든 탭에.
  • 토큰 저장 — access는 메모리에만, refresh는 httpOnly 쿠키로 회전. 스크립트가 꺼낼 수 있는 저장소에 토큰을 두지 않습니다.
  • 새 탭 — 메모리가 비어 있는 새 탭은 BroadcastChannel로 다른 탭에 REQUEST_TOKEN을 보내고 TOKEN_RESPONSE를 받아 세션을 이어받습니다. 로그아웃도 같은 채널로 모든 탭에 전파.
  • 동시 401 — refresh가 진행 중이면 같은 Promise를 돌려주고, 아니면 플래그를 세우고 공유 Promise를 만듭니다. 동시에 401을 받아도 refresh는 1회(트러블슈팅 ④).
  • 테스트 — axios 어댑터만 mock한 Jest spec 5케이스. 동시 401 두 건에서 refresh 1회, 원 요청 2 + 재시도 2 = 4회를 단언.
  • 컴포넌트 axios 직접 호출 0건 — public/auth 클라이언트 분리로 공개 호출에 토큰 누출 방지.

Overview

운영 중인 E-커머스에서 에러가 나면 폰으로 알림을 받고, AI가 소스 코드를 읽어 원인과 조치를 정리하고, 사람이 그 분석을 스와이프로 채점합니다. 채점 결과는 프롬프트·도구 구성별로 비교되고, 승인된 분석대로 실제 코드를 고친 뒤 재현 스크립트와 Sentry로 다시 확인하는 데까지 이어집니다. 앱에는 푸시·딥링크·생체 잠금·제스처처럼 웹으로는 안 되는 것만 담았고, 같은 RN 코드의 웹 빌드로 설치 없이 체험할 수 있게 했습니다. 인시던트 7건 · 평가자 1명인 작은 표본이라, 결과는 "증명"이 아니라 "확인"으로 적습니다.

AI 분석 — 소스를 읽고 원인과 조치를 정리
Sentry 이슈의 스택만 보고 추측하지 않도록, AI가 스택에 나온 파일을 직접 읽게 했습니다.
  • 코드 읽기 도구 — 스택의 파일을 읽되 허용 폴더만, 한 번에 80줄씩. 여기에 배포 사실 4줄(어디에 어떻게 배포되는지)을 붙여 원인·추천 조치·확신도를 JSON으로 받습니다.
  • 화면 — 확신도 배지, 원인과 추천 조치를 나눠 보여주고 각각 복사할 수 있습니다. 예시 코드가 길어도 화면을 넘치지 않게 스크롤.
  • 4가지 구성 비교 — 같은 이슈를 프롬프트·도구 유무가 다른 4가지 구성으로 분석하고, 블라인드 채점 결과로 버전별 승인율·별점을 비교합니다.
  • 정답 메모는 LLM에 넣지 않음 — 채점용 사실 메모가 분석 입력에 섞이지 않는다는 것을 테스트로 고정했습니다.

Overview

객체 탐지 결과(COCO·YOLOv8)를 보통 2D 박스로만 보는 것과 달리, 같은 결과를 2D 이미지와 3D 공간에서 동시에 탐색합니다. 한 객체를 어느 뷰에서 선택하든 4개 뷰(2D·3D·리스트·분석)가 동시에 같은 객체를 가리키도록 설계했고, nuScenes 실측 3D를 데이터 스위처로 붙여 이미지에서 추정한 3D와 실제 측정된 3D를 한 화면에서 비교합니다. 데이터 소스가 정적 JSON인 클라이언트 SPA입니다 — R3F Canvas라 전 페이지가 클라이언트 렌더링이며, SSR 경험으로는 적지 않습니다.

시스템 구조

정적 JSON → lib/ 순수 함수 계층(parser·estimator·selector)이 외부 입력을 unknown으로 받아 isCocoDataset 타입 술어로 검증 후 내부 Frame[]로 변환 → Zustand store(단일 선택 상태) → 스토어를 구독하는 곳은 page 하나로 두고, slice selector로 필요한 조각만 읽어 selectedId·onSelect를 props로 내려줍니다. lib/와 components/를 분리해 좌표 변환(global → ego → three)까지 React 밖에서 JSDOM 없이 테스트했습니다.

기술 선택 — 정적 JSON 하나에 맞춰 도구를 덜어냈습니다
  • Three.js + React Three Fiber + drei — 2D와 같은 데이터를 3D 공간에 선언적으로 렌더링
  • Zustand 5 — 4개 뷰가 공유하는 상태를 미들웨어 없는 76줄 단일 스토어로
